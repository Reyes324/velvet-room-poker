# 架构设计原则（跨平台可复用）

这份文档记录的是**设计策略**，不是这个项目的具体实现细节——目的是即使以后整个技术栈换掉（比如从网页搬去做原生 App），这些判断逻辑还能直接套用。具体的 bug 记录、文件路径、代码片段，仍然记在 `openspec/changes/*/design.md` 里；这里只留"为什么这么设计"和"什么时候该用这条原则"。

---

## 原则一：瞬时反馈要靠"事件流"驱动，不能靠"读最新状态"推导

### 问题的形状

系统里有两类完全不同的东西，容易被当成同一类东西处理：

1. **持续状态（state）**：任意时刻只有一个"当前值"，新的值会覆盖旧的值——比如"底池现在多少钱"“轮到谁行动”。只关心"现在是什么"，不关心"经历了几次变化"。
2. **离散事件（event）**：每一次发生都是独立的、都需要被感知到——比如"谁做了什么操作"“谁说了一句话”“提示音要不要响一下”。每一次都重要，哪怕来得很快很密集。

如果用第 1 类的处理方式（"观察某个字段的最新值，变了就反应一下"）去实现第 2 类需求（"每次真实发生都要有一次反应"），会有一个根本性的坑：**当多次事件发生得足够快、快过你的观察循环能区分它们的速度时，"最新值"这个字段会被连续覆盖，中间发生过的事件就会在你观察到之前就已经消失，你的反应逻辑永远只会对"最后一次"有反应，前面几次是彻底丢失，不是延迟，是从来没被看见过。**

### 判断标准：这个需求是"状态"还是"事件"？

问自己一句话：**"如果这件事快速发生了 3 次，我的界面应不应该有 3 次反应？"**
- 应该有 3 次反应（3 个提示音、3 条气泡、3 条日志）→ 这是事件，必须用事件流驱动。
- 只应该反映"最终结果"（比如"底池现在是多少"）→ 这是状态，用最新值驱动没问题。

### 正确的实现方式

- 事件源头（服务端/后端）：每一次真实发生，都单独发一条消息出去，不要把多次发生合并成一条"最新状态"广播。
- 接收端：订阅这条独立的事件消息流，**直接在收到每一条消息的那个回调里做反应**，不要把这个反应逻辑挂在"观察某个聚合状态是否变化"的监听器上（这类监听器在大多数 UI 框架里，只在一次"渲染/观察"周期里跑一次，会把这个周期内发生的多个底层事件合并成一次观察）。
- 这个模式生效的前提是：事件消息的传输通道本身**保证按发送顺序送达**（单条 TCP/WebSocket 连接天然满足；如果换了不保证顺序的传输方式，要么自己加序号去重排序，要么换一个有序的通道）。

### 反例信号（看到这些就要警惕）

- 代码里有一个"当前最新的一次 XXX"字段（单槽位，不是一个列表/队列），却被多个不同来源的 UI 反应共同依赖。
- 通过"对比这一次的状态快照和上一次的状态快照有什么不同"来推断"发生了什么事"（diff-based inference）——这类推断在源头能一次性产出多个变化时，天然只能看到"最终净效果"，看不到过程中的每一步。
- 注释/代码里出现"这个不会有问题，因为用了合并式更新（函数式 setState 之类）"这种论证——要追问一句：**是"每次真实事件都调用了一次这个合并更新"，还是"只在某个聚合状态变化时调用了一次"？** 前者才是安全的，后者不是，即使更新函数本身写得很"正确"，调用它的时机不对，照样会丢数据。

### 这个项目里踩过两次的同一个坑（具体记录见对应 design.md 条目）

1. **动作提示音偶发不响**——声音原本挂在"观察最新游戏状态"的监听器上，AI 连续快速行动时，多次状态广播被前端渲染框架合并成一次观察，只有最后一个动作的声音会响。
2. **对手的动作提示气泡偶发完全不出现**——跟上面同一个根因，只是表现在气泡而不是声音上。

两次都是同一个原则被违反、只是表现在不同的 UI 反馈上——说明这不是"这一处代码写错了"，是"这一类需求（离散事件反馈）一开始就选错了实现范式"，值得当成设计阶段就该规避的模式，而不是等出现一次修一次。

**换平台/换技术栈时怎么套用**：不管是原生 App 收 WebSocket/长连接推送，还是别的实时通信方案，只要界面上有"事件发生就要有对应反馈"（提示音、动画、气泡、日志、震动反馈……）这类需求，一开始就应该设计成"每条独立事件消息各自触发一次反应"，而不是"观察某个共享状态变了没有"——不要等测出"偶发丢失"这类难复现的 bug 才回头改。
