# 用户反馈系统 设计文档

## 背景

用户（连同一起打牌的朋友们）目前只能通过口头/聊天把 bug 和建议转达给我，中间容易丢失细节、也没有留痕。用户希望网页上直接开一个反馈入口，让朋友们自己提（文字+图片），后端把这些反馈收集起来，我定期评估、按产品定位筛选，能自动修的 bug 自动修掉，同时网站上要能看到产品在持续迭代（更新日志）。

## 关键约束：Render 免费档没有持久化磁盘

这条约束决定了整个存储架构。项目部署在 Render 免费档，本地文件系统在**每次 `git push` 触发的重新部署**时都会被清空重置——这正是本次会话里"人机对战牌局重置、对手名字也变了"那个 bug 的根因（`server/data/pveProfiles.json` 这类本地 JSON 文件不受影响是因为它相对不常写，但反馈系统会频繁触发部署，因为"处理反馈"这个动作本身就是推代码）。所以反馈数据**不能**存成本地文件，必须放在部署周期之外持久化的地方。

## 方案：反馈存成 GitHub Issue

网页提交的反馈，由服务器通过 GitHub API 直接创建一个 GitHub Issue：

- 图片（如果有）先通过 GitHub Contents API 提交到仓库的 `feedback-attachments/` 目录，拿到 `raw.githubusercontent.com` 的直链。
- 用文字 + 图片直链（markdown 图片语法）拼成 Issue 正文，避免图片走 base64 撑爆 Issue 正文长度限制。
- 新建的 Issue 自动打 `feedback` 标签，标题取反馈文字前若干字。

选这个方案而不是引入数据库/第三方服务：不依赖 Render 本地磁盘、天然持久化、公开可追溯（用户自己也能在 GitHub 上看到处理进度）、我本来就有 GitHub CLI 工具能直接读写 Issue，不需要新增任何依赖或账号体系。

服务器需要一个只有这个仓库读写权限的 GitHub Personal Access Token（细粒度 token，Issues + Contents 权限设成 Read and write，其余权限默认不给），存成 Render 的环境变量 `FEEDBACK_GITHUB_TOKEN`，不进代码、不进 git。

## 1. 反馈入口 & 提交流程

- 常驻的轻量入口（跟现有"人机对战"/"刷新"链接同一视觉层级），文案类似"问题反馈"。出现在首页和游戏内（房间/PVE 都能点到）——多数反馈很可能是"打着打着发现不对劲"，希望不用离开当前页面就能报。
- 点开是一个弹窗：文字描述框（必填）+ 图片上传（可选，最多 1 张，客户端先压缩/限制尺寸——长边压到 1600px 以内、控制在 2MB 以内再上传）+ 提交按钮。
- 完全匿名，不收集昵称/设备 id，跟产品现在"不需要登录"的风格一致。
- 提交成功后弹窗关闭，给一个简短的"已收到，谢谢反馈"提示。

## 2. 评判标准（紧扣产品定位）

产品定位：面向"喜欢德州扑克、想跟朋友一起玩、无聊时也想跟电脑练手、希望提升牌技和找到乐趣"的人群。

每条反馈过一遍这个标准，打两个维度的标签：

- **类别**：`bug`（功能/规则/连接性缺陷）、`design`（产品设计类，比如 UI/AI 打法风格/新功能想法）、`off-topic`（跟这个产品定位无关，或者会伤害其他玩家体验的要求，比如破坏游戏公平性的建议）
- **状态**：`accepted`（认可，值得处理，可能已经修了或者需要人来定design）、`wontfix`（拒绝，附带具体理由）

不管接受还是拒绝，都在 Issue 里写一条评论说明判断理由——即使拒绝了，提反馈的人也能在 GitHub 上看到"为什么没采纳"，不是石沉大海。

## 3. 定时审核 & 自动修复的边界

- 用当前会话环境自带的定时唤醒能力，**每天一次**自动醒来，拉取所有还没处理过的 `feedback` 标签 Issue；用户也可以随时手动喊我检查，不用等定时任务。

> **实施结果（2026-08-02，Task 7 记录）**：规划阶段把上面这句话具体化为"用 `RemoteTrigger`，不用 `CronCreate`"——`CronCreate` 是会话级的，创建它的会话一结束就没了，且不管会话是否还在都会在 7 天后硬性自动过期，不适合"每天一次、长期运行"的需求。但实际执行这一步时，`RemoteTrigger` 的 `create` 动作被账号配置卡住：需要一个账号级的 `job_config.ccr.environment_id`（或 `self_hosted_runner_pool_id`），且没有任何发现机制——`RemoteTrigger` 自己的 `list` 返回空，也没有工具能枚举合法的 environment id。这个问题升级给了用户，用户选择先用 `CronCreate` 顶上（job id `9885f659`，schedule `17 3 * * *` = 每天本地时间 3:17，recurring）。**这是明确的临时垫档方案，不是这里设计的持久方案**：7 天后按工具自身限制自动失效，创建它的 Claude 会话结束也会立刻失效，需要人工定期续期；要变成真正的 `RemoteTrigger` 长期方案，需要用户先在自己的 claude.ai 账号上找到/配置一个 `environment_id`（当前位置未知，需要用户自己排查），这是一项跟这轮功能实施范围无关的后续待办，本文档的设计意图（每天一次、长期自动运行）保持不变，只是记录当前用的是哪个机制在顶替它。
- 对每一条：按 Section 2 的标准分类、打标签、写评估理由评论。
- 只有同时满足以下**全部**条件，才允许自动修复 + 测试 + 推送到线上，否则一律留给下次真人对话一起处理：
  1. 类别是 `bug`（不是 `design`/`off-topic`）
  2. 反馈里的复现步骤足够具体，能在代码里独立定位到根因（不是"感觉哪里怪怪的"这种模糊描述）
  3. 修复不涉及产品/视觉/AI 打法风格这类需要人拍板的决策
  4. 改动范围小（几个文件以内），不是结构性重构
- 满足才修：走这次会话一直在用的同一套流程——先找根因、写回归测试、跑全量测试通过才提交，commit message 里带上对应 Issue 号；修完直接在 Issue 里评论说明做了什么、测试情况，然后关闭这个 Issue。
- 不满足就只写评估评论，Issue 保持打开，等下次真人对话一起看，不会自己去改代码。
- 每一次处理（不管是自动修复了，还是只是分类评估）都往 Section 4 的更新日志追加一条记录。

## 4. "最近更新"展示

- 首页加一个不打扰的小入口（跟"刷新"链接同一视觉层级），点开显示一个更新日志列表，每条带日期时间，最新的在最上面。
- 日志内容是给玩家看的、简短口语化的一句话（比如"修复了：气泡有时候会卡在上一轮"），不是内部 SDD `tasks.md` 那种详细技术记录。
- 存储：日志文件（比如 `client/src/changelog.json`）跟随正常代码一起提交/部署，构建时随包发布——不需要额外的运行时存储，天然跟"这次代码改动"绑在一起，逻辑上也更准确（这条日志描述的就是这次部署带来的变化）。

## 数据流

```
玩家点"问题反馈" → 填文字+可选图片 → 提交
  → 服务器：图片先提交到 GitHub Contents API（feedback-attachments/）
  → 服务器：创建 GitHub Issue（文字 + 图片直链），打 feedback 标签
  → 玩家看到"已收到"提示

每天一次（或用户手动触发）：
  → 拉取未处理的 feedback Issue
  → 逐条按产品定位评估，打 类别/状态 标签，写评估理由评论
  → 若同时满足"bug + 复现清晰 + 不涉及产品决策 + 改动小"：
      自己修 → 写回归测试 → 跑全量测试 → 提交推送 → 评论 + 关闭 Issue
    否则：
      只写评估评论，Issue 保持打开，留给下次真人对话
  → 每次处理都往 client/src/changelog.json 追加一条用户可读的记录

玩家点首页"最近更新" → 看到 changelog 列表，最新在最上面
```

## 明确不做（这轮范围之外）

- 不做反馈提交者的身份识别/账号体系——完全匿名，跟产品现状一致。
- 不做"design 类"反馈的自动实现——涉及产品/视觉/AI 风格决策的，永远留给真人对话决定，定时任务只负责分类和评估理由，不动手改。
- 不引入数据库/第三方反馈服务——GitHub Issue 本身就是存储层，足够这个体量使用。
- 不做反馈的垃圾/滥用防护（比如验证码、频率限制）——面向的是一小群认识的朋友，暂不需要；如果以后真的遇到滥用问题，再单独加。
