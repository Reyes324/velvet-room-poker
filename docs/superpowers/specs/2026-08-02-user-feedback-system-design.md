# 用户反馈系统 设计文档

## 背景

用户（连同一起打牌的朋友们）目前只能通过口头/聊天把 bug 和建议转达给我，中间容易丢失细节、也没有留痕。用户希望网页上直接开一个反馈入口，让朋友们自己提（文字+图片），后端把这些反馈收集起来，我定期评估、按产品定位筛选，能自动修的 bug 自动修掉，同时网站上要能看到产品在持续迭代（更新日志）。

## 关键约束：Render 免费档没有持久化磁盘

这条约束决定了整个存储架构。项目部署在 Render 免费档，本地文件系统在**每次 `git push` 触发的重新部署**时都会被清空重置——这正是本次会话里"人机对战牌局重置、对手名字也变了"那个 bug 的根因（`server/data/pveProfiles.json` 这类本地 JSON 文件不受影响是因为它相对不常写，但反馈系统会频繁触发部署，因为"处理反馈"这个动作本身就是推代码）。所以反馈数据**不能**存成本地文件，必须放在部署周期之外持久化的地方。

## 方案：反馈存成 GitHub Issue

网页提交的反馈，由服务器通过 GitHub API 直接创建一个 GitHub Issue：

- 图片（如果有）先通过 GitHub Contents API 提交到仓库的 `feedback-attachments/` 目录，拿到 `raw.githubusercontent.com` 的直链。
- 用文字 + 图片直链（markdown 图片语法）拼成 Issue 正文，避免图片走 base64 撑爆 Issue 正文长度限制。
- 新建的 Issue 自动打 `feedback` 标签，标题取反馈文字前若干字。

选这个方案而不是引入数据库/第三方服务：不依赖 Render 本地磁盘、天然持久化、公开可追溯（用户自己也能在 GitHub 上看到处理进度）、我本来就有 GitHub CLI 工具能直接读写 Issue，不需要新增任何依赖或账号体系。

服务器需要一个只有这个仓库读写权限的 GitHub Personal Access Token（细粒度 token，Issues + Contents 权限设成 Read and write，其余权限默认不给），存成 Render 的环境变量 `FEEDBACK_GITHUB_TOKEN`，不进代码、不进 git。

## 1. 反馈入口 & 提交流程

- 常驻的轻量入口（跟现有"人机对战"/"刷新"链接同一视觉层级），文案类似"问题反馈"。出现在首页和游戏内（房间/PVE 都能点到）——多数反馈很可能是"打着打着发现不对劲"，希望不用离开当前页面就能报。
- 点开是一个弹窗：文字描述框（必填）+ 图片上传（可选，最多 1 张，客户端先压缩/限制尺寸——长边压到 1600px 以内、控制在 2MB 以内再上传）+ 提交按钮。
- 完全匿名，不收集昵称/设备 id，跟产品现在"不需要登录"的风格一致。
- 提交成功后弹窗关闭，给一个简短的"已收到，谢谢反馈"提示。

## 2. 评判标准（紧扣产品定位）

产品定位：面向"喜欢德州扑克、想跟朋友一起玩、无聊时也想跟电脑练手、希望提升牌技和找到乐趣"的人群。

### 2.1 四点评估框架（2026-08-12 定稿，权威版本，同步写在 `CLAUDE.md`）

`bug` 类反馈（有明确复现路径、能定位根因的）直接走 Section 3 的自动修复流程，不需要过下面这套框架——那是给功能性缺陷用的，判断标准是"根因对不对、修法对不对"，不是要不要做。

`design`/新功能类反馈，每条都要**分别写出**这四点的具体判断，不能只写一句笼统的"design/accepted，留给真人决策"糊弄过去：

1. **需求合理性**——这个想解决的问题本身站不站得住脚，是不是真问题。
2. **当前阶段的必要性**——项目目前是"只有少量几个玩家"的朋友局阶段。合理 ≠ 现在就该做，很多在大规模场景下合理的功能，现阶段未必有必要。
3. **成本、收益、风险**：
   - 成本：不只是要不要花钱，还包括开发成本、后续维护成本。
   - 风险：会不会有合规问题、会不会跟其他已有产品设计/决策打架。
4. **产品复杂度守门**（独立于上面三条之外必须单独过一遍）：这个功能会不会让产品分支变多、变臃肿？一个"合理、当前也有必要、成本收益都划算"的功能，如果会让交互逻辑/权限模型长出一堆新分支，也要慎重，尤其是提反馈的人没有给出足够背景/动机的情况下。

四点里任何一点判断是"证据不足、暂不评估"，都要明说，不能跳过不提。

### 2.2 标签 + 评论

每条反馈打两个维度的标签：

- **类别**：`bug`（功能/规则/连接性缺陷）、`design`（产品设计类，比如 UI/AI 打法风格/新功能想法）、`off-topic`（跟这个产品定位无关，或者会伤害其他玩家体验的要求，比如破坏游戏公平性的建议）
- **状态**：`accepted`（认可，值得处理，可能已经修了或者需要人来定design）、`wontfix`（拒绝，附带具体理由）

不管接受还是拒绝，都在 Issue 里写一条评论说明判断理由——即使拒绝了，提反馈的人也能在 GitHub 上看到"为什么没采纳"，不是石沉大海。`design` 类走 2.1 的四点框架，`bug`/`off-topic` 按各自类别给出具体理由即可，不用套四点模板。

**评论话术要求（2026-08-12 定稿）**：这些回复用户自己能在 GitHub 上看到，语气会直接影响提反馈的人的体验，不希望让人觉得被挫伤。

- 结论先行、简明扼要——先说定论（接受 / 暂不做 / 拒绝），再给一两句关键原因，不要堆砌评估过程、条件罗列、大段分析。
- `wontfix` 或"暂不做"时，尽量给出一个具体的方向，建议对方补充更详细的原因/使用场景/复现步骤——不是单纯说"不做"，而是留一条"如果你能说清楚背景，我们可以再看"的路，语气友善。

### 2.3 评论篇幅

这条只对**真人已经在对话里讨论、拍板过的反馈**生效（定时任务自己独立评估的、还没被真人过一遍的，仍然按 2.1/2.2 正常写清楚判断）：一旦这条反馈的结论是真人在对话中定的，回填到 Issue 的评论就只需要言简意赅地总结结论（一两句话：定了什么、如果有用一句话说明原因），不用重复展开当时讨论过的取舍分析。

## 3. 定时审核 & 自动修复的边界

- 用当前会话环境自带的定时唤醒能力，**每天一次**自动醒来，拉取所有还没处理过的 `feedback` 标签 Issue；用户也可以随时手动喊我检查，不用等定时任务。

### 3.1 需要用户决策的反馈——怎么通知、怎么闭环（2026-08-12 定稿）

`design`/需要人拍板的反馈，routine 自己不会去猜结论，但也不能就这么石沉大海地一直晾着。跟用户确认过可行方案后定的机制：

- **通知渠道**：不新增任何东西——直接依赖 GitHub 自带的 issue 通知（routine 评论/打标签时，仓库主人 `Reyes324` 会按自己的 GitHub 通知设置收到邮件/App 推送）。曾经考虑过 `ntfy.sh` 这类第三方推送服务，但那是单向的、不能直接回复，被否决；`PushNotification`（Claude Code 本地终端/手机推送）也不可行——那个工具只能推给发起它的那个交互式 session 自己配对的终端/手机，routine 是独立的云端隔离会话，拿不到这个工具。
- **回复即决策**：用户看到通知后，直接在对应 GitHub issue 下面评论回复即可，不需要专门的界面或流程。
- **下次运行自动读取并执行**（闭环）：routine 每次运行的第一步是拉一遍所有 open 的 `feedback` issue；如果发现某条 issue 最新一条评论是 `Reyes324` 发的、且是在 routine 自己之前留的评估评论**之后**，就认定这是用户给出的决策，按用户说的执行（关闭/保持 P2/如果是同意的 bug 修复就走正常的自动修复流程）——不需要用户再专门跑一次别的操作，第二天凌晨的例行运行就会自动处理。回复不够明确（反问、补充信息但没表态）时不猜测执行，只留追问评论。
- 这条机制的完整实现细节（识别"用户已回复但未处理"的判断逻辑、评论话术里提醒用户可以直接回复）写在 routine 自己的 prompt 里（`trig_014hQaj11hsgnCLecf5dvQZb`，管理入口见上文），这份文档只记录设计决策，不重复贴 prompt 全文——两者理论上应保持一致，改动时两边都要同步。

> **实施结果（2026-08-02，Task 7 记录）**：规划阶段把上面这句话具体化为“用 `RemoteTrigger`，不用 `CronCreate`”——`CronCreate` 是会话级的，创建它的会话一结束就没了，且不管会话是否还在都会在 7 天后硬性自动过期，不适合“每天一次、长期运行”的需求。但实际执行这一步时，`RemoteTrigger` 的 `create` 动作被账号配置卡住：需要一个账号级的 `job_config.ccr.environment_id`，且当时没有任何发现机制。这个问题升级给了用户，用户选择先用 `CronCreate` 顶上（job id `9885f659`），并明确记录为临时垫档。
>
> **实施结果（2026-08-07 更新，blocker 已解除）**：`CronCreate` 垫档如预期失效了——7 天过期 + 创建它的会话结束，两个条件都触发，`CronList` 与 `RemoteTrigger list` 均为空，期间 Issue #7 无人处理。同日发现 `environment_id` 现在**可以枚举**（`Default` / `env_01WiZuy2n9EsiJy7BxMDpBbg`），原 blocker 解除，遂按本文档最初的设计意图建立了持久的云端 routine：
>
> - routine id：`trig_014hQaj11hsgnCLecf5dvQZb`（名称「velvet-room-poker 每日反馈闭环」）
> - 排期：`0 19 * * *` UTC = **每天北京时间凌晨 3:00**
> - 模型：`claude-sonnet-5`。曾短暂设为 opus-5，随后改回：真正的安全防线是“四条准入条件 + 测试不全绿不推送”的门禁，而非模型强弱，且此 job 多数日子只做打标签评估。
> - 运行环境：Anthropic 云端隔离会话，独立 clone 本仓库，**与用户本机开关机无关**——这正是 `CronCreate` 做不到的那一点。
> - 推送授权：用户于 2026-08-07 明确授权“**bug 类修复可直接推 main**，需要决策的才找我讨论”。这是对平时“不经同意不 push”规矩的一项**限定例外**，仅限本 routine、仅限 bug 类、仅限测试全绿时。
> - 管理入口：https://claude.ai/code/routines/trig_014hQaj11hsgnCLecf5dvQZb （删除 routine 只能在这个页面操作）
- 对每一条：按 Section 2 的标准分类、打标签、写评估理由评论。
- 只有同时满足以下**全部**条件，才允许自动修复 + 测试 + 推送到线上，否则一律留给下次真人对话一起处理：
  1. 类别是 `bug`（不是 `design`/`off-topic`）
  2. 反馈里的复现步骤足够具体，能在代码里独立定位到根因（不是"感觉哪里怪怪的"这种模糊描述）
  3. 修复不涉及产品/视觉/AI 打法风格这类需要人拍板的决策
  4. 改动范围小（几个文件以内），不是结构性重构
- 满足才修：走这次会话一直在用的同一套流程——先找根因、写回归测试、跑全量测试通过才提交，commit message 里带上对应 Issue 号；修完直接在 Issue 里评论说明做了什么、测试情况，然后关闭这个 Issue。
- 不满足就只写评估评论，Issue 保持打开，等下次真人对话一起看，不会自己去改代码。
- 每一次处理（不管是自动修复了，还是只是分类评估）都往 Section 4 的更新日志追加一条记录。

## 4. "最近更新"展示

- 首页加一个不打扰的小入口（跟"刷新"链接同一视觉层级），点开显示一个更新日志列表，每条带日期时间，最新的在最上面。
- 日志内容是给玩家看的、简短口语化的一句话（比如"修复了：气泡有时候会卡在上一轮"），不是内部 SDD `tasks.md` 那种详细技术记录。
- 存储：日志文件（比如 `client/src/changelog.json`）跟随正常代码一起提交/部署，构建时随包发布——不需要额外的运行时存储，天然跟"这次代码改动"绑在一起，逻辑上也更准确（这条日志描述的就是这次部署带来的变化）。

## 数据流

```
玩家点"问题反馈" → 填文字+可选图片 → 提交
  → 服务器：图片先提交到 GitHub Contents API（feedback-attachments/）
  → 服务器：创建 GitHub Issue（文字 + 图片直链），打 feedback 标签
  → 玩家看到"已收到"提示

每天一次（或用户手动触发）：
  → 拉取未处理的 feedback Issue
  → 逐条按产品定位评估，打 类别/状态 标签，写评估理由评论
  → 若同时满足"bug + 复现清晰 + 不涉及产品决策 + 改动小"：
      自己修 → 写回归测试 → 跑全量测试 → 提交推送 → 评论 + 关闭 Issue
    否则：
      只写评估评论，Issue 保持打开，留给下次真人对话
  → 每次处理都往 client/src/changelog.json 追加一条用户可读的记录

玩家点首页"最近更新" → 看到 changelog 列表，最新在最上面
```

## 明确不做（这轮范围之外）

- 不做反馈提交者的身份识别/账号体系——完全匿名，跟产品现状一致。
- 不做"design 类"反馈的自动实现——涉及产品/视觉/AI 风格决策的，永远留给真人对话决定，定时任务只负责分类和评估理由，不动手改。
- 不引入数据库/第三方反馈服务——GitHub Issue 本身就是存储层，足够这个体量使用。
- 不做反馈的垃圾/滥用防护（比如验证码、频率限制）——面向的是一小群认识的朋友，暂不需要；如果以后真的遇到滥用问题，再单独加。
