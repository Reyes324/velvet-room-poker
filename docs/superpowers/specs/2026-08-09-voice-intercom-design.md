# 语音对讲 设计文档

## 背景

用户希望给牌桌加入语音对讲功能，让朋友们打牌时能语音喊话/调侃，让线上局更接近线下面对面打牌的体验。本轮决策通过多轮"成本/收益/风险"讨论确认（用户是产品设计师，非技术背景），具体实现细节交由实现阶段决定。

## 关键约束

- 部署在 Render 免费档，服务器带宽/算力有限，不能承担持续的语音流量转发。
- 牌桌人数上限 8 人（含 AI，AI 不需要语音）。
- 已有实时通道：socket.io，用于同步游戏状态，可以复用。

## 方案：WebRTC 点对点直连（mesh），复用现有 socket.io 做信令

- 语音数据不经过咱们服务器，玩家设备之间直接建立连接（点对点）；服务器只负责最初的"牵线搭桥"（信令），复用现有 socket.io 连接，不引入新基础设施，不产生额外服务器成本。
- 房间内每个玩家与其他每个玩家之间各建立一条独立连接（mesh），从用户体验看等同于广播——按住说话，房间内所有人都能听到，用户感知不到底层是多条独立连接。
- 8 人桌规模下 mesh 连接数（每人最多 7 条并发连接）在浏览器/设备性能范围内，无需引入更复杂的转发架构（SFU）；如果以后牌桌规模远超当前上限，需要换方案，不在本轮范围内。
- 房间之间完全隔离：mesh 只发生在同一房间内部，房间数量增加不会让单个房间的连接复杂度上升。
- 故障隔离：每对连接互相独立，某一方网络不稳定只影响其与他人之间那条连接的质量，不会拖累房间内其他人彼此的连接——这是相对于"集中转发"架构的结构性优势，避免单点故障拖累全桌语音。

## 借助的开源方案 —— ~~simple-peer~~ 已撤销，改用浏览器原生 API（2026-08-09 实测后推翻）

**原决策**：用 `simple-peer` 处理点对点连接的建立与维护，理由是"成熟、被广泛使用、成功率高"。

**推翻理由（都是实测出来的，不是查资料）**：

1. **它已经三年半没有发版**（最后一版 9.11.1，2023-01-26）。"成熟"成立，"还在维护"不成立——当初向用户推荐时把这两件事说成了一件。
2. **装上之后整个 App 白屏**。`npm install simple-peer` 后仅仅 `import` 一下，`vite build` **构建照常通过**（只打了一条 `Module "events" has been externalized` 的警告），但真实浏览器打开首页直接 `PAGEERROR: global is not defined`、body 全空——**不是语音页面坏掉，是整站打不开**。这正是 CLAUDE.md 那条规矩要防的情形：构建绿、真机死。
3. 附带成本：bundle 从 322 kB 涨到 414 kB（gzip 100 → 127 kB），对一个主要在手机上打开的页面不划算。

要救回来得手动补 `global`/`Buffer`/`process` 这些 Node 垫片配置——为一个停更三年的库增加构建复杂度，性价比是负的。

**新决策**：直接用浏览器原生的 `RTCPeerConnection`，不引入任何 WebRTC 依赖。依据同样来自实测而非推断——`/voice-check` 自检页里那段完整的 SDP 协商 + ICE 流程本来就是原生写的、约 50 行、已经在真实浏览器里跑通并有 e2e 守着。`simple-peer` 包的正是这一层，而我们已经证明这一层自己写得住。

牌桌相关的交互（按住说话、说话状态提示、信令编排）本来就要自己实现，这一点不变。

## 交互形式：按住说话（push-to-talk）

- 不做常开麦克风：一是避免多人同时说话时的回声/串音，二是更符合"对讲"的产品语义。
- **用户已确认选择按住说话**（2026-08-09）。提出过一个反对意见供其权衡：手机上牌桌底部就是下注/弃牌操作区，按住说话要长期占用一只手，跟出牌操作有冲突，因此建议过"一键开麦/闭麦"切换式。用户仍选择按住说话。**记录在案作为上线后真机实测的重点关注项**——如果实测下来确实妨碍出牌，再回到这个决策重新讨论，而不是当场加一个并行的第二套交互。

## 麦克风权限申请时机：点击「说话」时才申请

- 不在进入牌桌时就申请，避免打扰根本不打算用语音的人。
- **这一条同时也是微信内置浏览器的硬性技术约束**，不只是产品偏好：微信里 `getUserMedia` 必须由用户主动点击/触摸事件触发，页面加载后自动调用会直接失败。两者要求一致，没有冲突。

## 说话中的提示：头像发光 + 麦克风图标

正在说话的人，牌桌上其座位头像边框亮起，并带一个小麦克风图标。一眼能认出是谁在说，不依赖玩家自己分辨声音。

## 关键风险：用户的实际使用场景是「微信里打开网页」

这是本轮讨论中浮现出的、**优先级高于其余所有实现细节**的风险点。用户和朋友们实际是在微信内置浏览器里打开这个网页玩的，而微信内置浏览器对麦克风/WebRTC 的支持情况存在真实的不确定性：

- **安卓微信**：用腾讯自研 X5 内核，一般支持 `getUserMedia`，但历史上有兼容性问题记录。
- **iOS 微信**：走 WKWebView，系统层面自 iOS 14.3 起支持 WebRTC，但有开发者反馈微信侧表现不一致。
- **共同约束**：必须由用户主动点击触发（与上面的权限时机决策一致）。
- **体验坑**：微信内每次重新打开网页可能都需要重新授权麦克风，不像常规浏览器授权一次即可记住。

查到的公开资料互相矛盾且大多是 2021 年前后的，按 CLAUDE.md「不接受纯手算/读代码（读文档）就下结论，要真机实测」这条规矩，**不能靠读资料给这个功能的可行性打包票**。

### 因此：先做「麦克风自检页」探路，再决定是否投入完整功能

- 一个极简的独立页面（路由 `/voice-check`），零新增依赖，用户在微信里打开点一下就能知道能不能用。
- 检测项要区分**"权限拿到了"和"声音真的在流动"**——这两件事不等价，微信环境下有拿到 stream 但收不到音频的报告。所以自检页必须有实时音量条，而不是只报一句"授权成功"。
- 同样区分**"WebRTC API 存在"和"真的能建立连接"**——用页面内本机自环连接验证，避免 API 只是存在但被阉割。
- 成本很小，收益是：能用则后续开发心里有底；不能用则直接省下整个功能的开发成本。

### 第一次真机实测结果（iOS 26.3 + 微信 8.0.75，2026-08-09）

| 项 | 结果 |
|---|---|
| HTTPS / getUserMedia / RTCPeerConnection / AudioContext | 全部存在 |
| 麦克风权限 | **拿到**（`iPhone麦克风｜muted=false｜state=live`） |
| 麦克风收到声音峰值 | **1.000（真的有声音）** |
| 本机自环点对点连接 | **失败**，8 秒超时；远端流「有」，报告的连接状态 `closed` |
| 穿过连接回来的声音峰值 | 0.000 |
| STUN 公网穿透 | 腾讯不可达；**小米、Google 均拿到公网地址** |

**最重要的一条结论：微信 iOS 里麦克风是通的。** 这是整个功能里最可能被平台一刀砍掉、也最没法绕开的一环，它过了，等于最大的那个未知数消掉了。

**但"点对点失败"这一条不能采信为结论**，因为复盘代码发现自检页本身有两个缺陷，第一次实测的数据正好踩在上面：

1. **超时分支先 `cleanup()` 再读 `iceConnectionState`** —— `cleanup()` 会 `close()` 掉连接，把状态冲成 `closed`。也就是说无论真实情况是卡在 `checking` 还是压根没开始，报告里永远显示 `closed`，**唯一有诊断价值的证据被自己抹掉了**。报告里那个 `closed` 不是症状，是 bug。
2. **本机自环在 iOS 上本来就有它自己的坑**：WKWebView 的 host 候选是 mDNS 混淆的 `xxxx.local`，同页两条连接要先解析才能配对；而**真实的两台设备之间走的是 STUN 拿到的公网地址，根本不依赖这条路径**。所以自环失败与"两台手机连不上"之间没有强因果。

而 STUN 三台里两台可达，恰恰是**更接近真实场景**的正面信号——真机之间的连接靠的就是它。

**已做的修正**（同一轮）：超时前先取证再清理，并把候选地址统计（总数／host／mDNS／srflx）写进报告；自环超时从 8 秒放宽到 15 秒，避免把"慢"误报成"不支持"；结论文案从"这个环境的 WebRTC 有问题，语音对讲做不了"改为**如实说"测不出来"**——原文案是这页最初要避免的假阳性的镜像版本，同样不可接受。

**由此得到的方法论结论：本机自环这条判据的效力被高估了。** 它能证伪（自环通过 ⇒ WebRTC 确实能用），但不能证否（自环失败 ⇏ 环境不支持）。真正的判据只有**两台真手机互相连一次**，这与 CLAUDE.md 里「不接受纯读代码/读资料下结论」是同一条规矩。

### 双机实测第二轮：同网络通，跨网络不通（2026-08-09 深夜）

两次实测，结论截然相反：

| 场景 | 结果 |
|---|---|
| 两台在**同一网络**（微信 iOS） | **通**——真的听见对方说话 |
| 两台在**不同网络**（一台 `NetType/4G`，另一台 WiFi） | **不通**——`ICE：failed`，对方声音峰值 0.000 |

**先确认已经拿下的东西**：微信 iOS 里麦克风、WebRTC、我们自己写的信令与建连链路**全都是好的**——同网络下真人听见了真人说话。失败的只有 NAT 穿透这一环。

**被推翻的是"极少数场景"这个前提。** 原判断认为跨网络失败罕见，不值得为此加中转。实测表明它不是边缘情况，而是**这个产品的主场景**：朋友各在各家、各用各的网络联机打牌，本来就意味着两端网络不同；"同一个 WiFi"才是少数。国内运营商移动网络普遍是 CGNAT（且多为对称型），STUN 学到的公网地址对对端无效，纯 P2P 在这种组合下打不通是必然而非偶然。

**因此 TURN 中继从"明确不做"改为"必须做"**——一个功能只在少数场景可用，等于不可用。这不是范围膨胀，是原始假设被证伪后的必然修正。

**代价必须说清楚**：TURN 是真的在中转音频，会实打实消耗带宽，因此不可能像 STUN 那样白嫖。这一条改变了整个功能的成本结构（从"零运营成本"变成"可能要花钱"），是需要用户拍板的产品决策，不是我能自行决定的技术细节。

**下一步（低成本取证，不花钱）**：先把免费公共 TURN 接进来让用户复测跨网络。能通则证明"加中继确实能解决"，届时再谈用免费额度还是付费；不通则要单独查（免费 TURN 多在境外，国内可达性本身就是变量），再谈自建。**在拿到这一轮证据之前不做付费决定。**

### 备选方案（自检失败时）

引导玩家用微信的「在浏览器中打开」跳到系统浏览器（Safari/Chrome）里玩——体验绕一点，但功能能保住。这条不预先实现，等自检结果出来再决定要不要做。

## 实施顺序

1. ~~**麦克风自检页**（先做，探路）~~ 已做，且已完成第一轮真机实测——**麦克风这关过了，点对点这关测不出来**（见上）。
2. ~~**插入一步：两台真手机的连通性实测**~~ **页面已实现（`/voice-pair`），等真机结果**（新增，2026-08-09）。第一轮实测暴露出本机自环判据不足以支撑 go/no-go，必须用真实的两端连接来定。做法是把自检页扩成"双机模式"：两台手机开同一个页面、经现有 socket.io 交换连接信息、真的建一条连接互相说话。
   - **这步的成本不是沉没成本**：双机模式要写的东西（信令事件编排 + 建连 + 音频收发）正是完整功能的内核，验证通过后可以直接长成正式功能，不是一次性的探针。
   - 只做两人一对一，不做 mesh、不接牌桌 UI——先把"到底连不连得上"这一个问题单独回答掉。
   - **已完成的实现要点**：服务端 `voice:join` / `voice:signal` / `voice:leave` 三个事件，与游戏状态完全解耦，只转发 SDP/ICE；**发起方由服务端一次性指定**（后进来的人发 offer），避免双方同时 offer 造成的偶发卡死；信令只在同一语音房间内转发。客户端 `/voice-pair` 支持 `?code=` 直达（微信里发链接点开即用）。
   - **验证到什么程度**：e2e 用两个**互相独立的浏览器上下文**经真实服务端信令建连，断言声音双向真的传到了。这条绿意味着"信令 + 建连 + 音频收发"这条链路本身是通的——真机上万一仍连不上，问题范围可直接收窄到网络环境/微信内核，不必怀疑我们自己的实现。
3. 双机实测通过后，再实现完整的语音对讲（mesh 扩展 + 按住说话 + 说话提示 + 接进牌桌）。
4. 双机实测不通过，才回到"备选方案"重新讨论，不硬做。
