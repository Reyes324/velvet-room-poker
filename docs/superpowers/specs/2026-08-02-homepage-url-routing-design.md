# 首页/URL 路由重构 设计文档

## 背景

用户反馈（多次）：

- "而且很严重！你这个人机对战的域名是没改的。也就是说，我重新刷新同样的主页网址，就一直卡在那了，回不去首页"（PVE 崩溃后无法脱身，因为 PVE 根本没有独立 URL——`/`（裸域名）本身就是 PVE 页面，刷新只是重新触发同一次崩溃）
- "我的主域名无论什么时候访问，都是在首页"——多人房间已经有 `/room/CODE` 这个 URL，但访问裸域名 `/` 时，只要本地有保存的房间标记，会静默自动恢复进那个房间，不会停在首页
- 用户进一步确认：不想要"静默自动恢复"，想要首页展示"正在进行的会话"，用户自己点进去

`server/index.js` 里已有的 `ErrorBoundary`（2026-08-02 早些时候加的"放弃这局，回首页"按钮）是这个问题的应急止血——本次是从路由结构层面解决根因。

## 现状（改动前）

- `client/src/App.jsx` 的 `useEffect` 在**每次加载**时无条件跑一段"冷启动会话恢复"逻辑：
  - 有 `vr_roomCode` 且 URL 没指向别的房间 → 直接 `pushState('/room/'+code)` 并渲染 `RoomPage`，不经过首页。
  - 没有房间标记，但 `vr_pveActive` 在 30 分钟窗口内 → 直接渲染 `PvePage`，同样不经过首页；`/`（裸域名）本身从来不是 PVE 的 URL，PVE 全程只在 `/` 上运行，无法用 URL 区分"在首页"还是"在 PVE 局中"。
  - 都没有 → 才真正渲染 `HomePage`。
- `/room/<CODE>` 是唯一存在的会话 URL；PVE 没有对应的 URL。
- 房间和 PVE 在客户端是互斥的：开始一个会清掉另一个的本地标记（`handleJoined`/`handlePve` 隐式via 已有的 leave 逻辑）。

## 改动后

### 1. URL 结构

| URL | 含义 | 行为 |
|---|---|---|
| `/`（裸域名，无论 query/state 如何） | 首页 | **始终**渲染 `HomePage`，不再有任何自动恢复到会话的逻辑。若本地有会话标记，首页会异步显示一张"继续上局"卡片（见下），但初始渲染永远是首页本身。 |
| `/room/<CODE>` | 多人房间 | 不变：直接渲染 `RoomPage` 并尝试加入/恢复该房间——无论是好友发来的邀请链接，还是从首页卡片点进去，还是浏览器直接输入/收藏这个地址，行为一致。 |
| `/pve`（新增，固定路径，不带 id） | 人机对战 | 新增：直接渲染 `PvePage` 并尝试恢复本机的 PVE 会话（`vr_pveActive`/`vr_pveLastActive`/`vr_pveSeatCount`，沿用现有 30 分钟窗口逻辑）。PVE 本身是纯个人对局，不需要分享，所以不需要在 URL 里带具体的会话 id——`vr_playerId`（`pveId`）已经通过 localStorage 确定身份，`/pve` 只是一个路由标记位，用来把"在 PVE 局中"和"在首页"这两个状态用 URL 区分开。 |

`pushState` 调用点：

- 加入/创建/恢复房间成功 → `pushState('/room/'+code)`（不变）。
- 从首页开始新的 PVE 局，或首页点击"继续上局"卡片进入 PVE → `pushState('/pve')`（新增；今天完全不碰 URL）。
- 离开房间（`handleLeave`）→ `pushState('/')`（不变）。
- 离开/放弃 PVE（`handlePveLeave`，含 `ErrorBoundary` 的"放弃这局，回首页"按钮）→ `pushState('/')`（不变，`ErrorBoundary` 那次已经是硬跳转，天然满足）。

### 2. 首页"继续上局"卡片

首页挂载时，如果本地存在会话标记（`vr_roomCode` 或 `vr_pveActive`——继续保持二者互斥，同一时间最多一个标记生效，最多展示 1 张卡片）：

1. 立即发一次轻量的存在性确认请求，不展示任何加载态，也不阻塞首页其余部分的渲染：
   - 房间：复用已有的 `room:peek`（原本是给邀请链接预览用的，语义完全匹配：只读、不加入、不改服务端状态）。
   - PVE：新增 `pve:peek`——`socket.on('pve:peek', ({ pveId }, cb) => ...)`，只读查询 `pveSessions.get(pveId)` 是否存在，存在则回 `{ exists: true, handNumber, seatCount }`（用于卡片文案），不存在回 `{ exists: false }`。不创建、不修改任何会话状态，跟 `room:peek` 的只读性质对齐。
2. 确认存在 → 渲染卡片："继续上局：房间 XXXXXX" 或 "继续上局：人机对战（第 N 手）"。点击 → 按上面的 `pushState` 表，跳转到对应 URL 并进入。
3. 确认不存在（服务端已回收）或请求出错/超时 → 不展示卡片，同时清掉本地的 `vr_roomCode`/`vr_pveActive`/`vr_pveLastActive`/`vr_pveSeatCount` 标记，避免下次还要再确认一次同一个已经死掉的会话。这跟现有 PVE 超过 30 分钟窗口后清标记的逻辑是同一个模式，只是触发条件从"纯本地时间戳"改成"服务端确认"。
4. 卡片渲染本身是首页初始渲染之后的一次异步更新（首页组件不因为等这个请求而延迟展示）——这个请求走的是首页本来就要建立的 socket 连接，实测应该在到达即可用的量级（Render 免费档冷启动除外，冷启动时首页本身也在等 socket connect，卡片自然随之出现，不需要额外处理）。

### 3. 与现有流程的整合

- **邀请链接**（`/room/<CODE>` 或 `?room=CODE`）：不变，依旧直接渲染 `RoomPage` 走加入流程，完全绕开首页卡片——这是明确的目的地导航，不是本次要收窄的"裸域名"场景。
- **浏览器后退键**：`App.jsx` 现有的 `popstate` 监听目前只 `setRoom(null)`。扩展为同时 `setPveName(null)`，否则从 `/pve` 后退不会正确回到首页视图。
- **崩溃恢复按钮**（`ErrorBoundary` 的"放弃这局，回首页"）：不需要改动——它已经是清标记 + 硬跳转 `/`，而 `/` 现在无条件是首页，语义天然对齐，反而比改动前更可靠（改动前如果标记没清干净，硬跳转到 `/` 仍可能被冷启动恢复逻辑重新带回 PVE；改动后这条路径已经不存在了）。
- **冷启动恢复逻辑**（`App.jsx` 那个大 `useEffect`）：从"页面每次加载都跑"收窄为"只在 URL 明确是 `/room/<CODE>` 或 `/pve` 时才跑"——本质上从"首页的隐藏行为"变成"这两个具体路由自己的加载逻辑"。`/` 路由不再执行这段代码，改由首页组件自己的 peek 调用接管"要不要引导用户回到会话"这件事。

## 数据流 / 状态图

```
访问 /                      → HomePage（无条件）
                                 │
                                 ├─ 无本地会话标记 → 就是普通首页，没有卡片
                                 │
                                 └─ 有本地会话标记 → 首页照常渲染，同时后台发 peek
                                         ├─ 确认存在 → 弹出"继续上局"卡片 → 点击 → pushState + 渲染对应会话
                                         └─ 确认不存在/出错 → 清本地标记，无卡片

访问 /room/<CODE>            → 直接进 RoomPage（邀请链接 / 卡片点击 / 手动收藏，行为一致）
访问 /pve                    → 直接进 PvePage（卡片点击 / 手动收藏 / "新开一局"后的 pushState，行为一致）

离开房间 / 放弃 PVE          → pushState('/') → 回到上面"访问 /"的分支
```

## 涉及文件（预告，实际以后续实现计划为准）

- `client/src/App.jsx`：冷启动 `useEffect` 收窄为按路由分支；`popstate` 扩展；新增 PVE 的 `pushState('/pve')` 调用点。
- `client/src/pages/HomePage.jsx`：新增"继续上局"卡片状态 + peek 请求。
- `client/src/hooks/useSocket.js`（如果 peek 需要独立于现有 room 相关 hook）：视实现计划里的实际接口需要决定。
- `server/index.js`：新增 `pve:peek` handler，紧邻现有的 `room:peek`。

## 明确不做（这轮范围之外）

- 不支持房间和 PVE 会话并存（首页最多展示 1 张"继续上局"卡片）——用户已确认继续保持现有互斥约束，不是这次要解决的需求。
- 不做"历史对局列表"（比如展示已经结束的、无法再继续的往局）——首页卡片只展示"当前仍然可继续"的单个会话，结束了就没有入口。
- PVE 的 URL 不携带具体会话 id（`/pve` 是固定路径）——身份仍然完全靠 `vr_playerId`/localStorage 确定，跟今天的模型一致，只是多了一个路由标记位。
